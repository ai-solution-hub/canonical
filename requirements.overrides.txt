# .github/workflows/pipeline-lock.yml resolves it on a linux-x86_64 runner

# drift check reds any PR whose committed lock differs. To regenerate: apply

# WHY: `commonforms` pulls BOTH `ultralytics` and `rfdetr`->`supervision`, and all
# three declare `opencv-python` (the FULL, X11-linked variant). That put
# opencv-python==5.0.0.93 in the closure alongside the intended
# opencv-python-headless==4.13.0.92, so which distribution satisfied `import cv2`
# was resolution-order-dependent — and when the full variant won, docling's
# always-on layout model (docling-ibm-models) failed with
# `ImportError: libxcb.so.1: cannot open shared object file` on EVERY PDF convert
# in the buildpacks image (gcr.io/buildpacks/builder:google-22 has no X11 libs).
# 69 occurrences in a single nightly run; 0 of 73 source_documents were .pdf.
#
# The marker below is never true on any platform, so the transitive requirement is
# dropped from the resolution entirely. `ultralytics` and `supervision` only ever
# `import cv2`, which opencv-python-headless supplies — they do not need the full
# variant's X11-linked GUI functions (cv2.imshow et al.), which the pipeline never
# calls.
#
# REJECTED ALTERNATIVE (owner decision, recorded so it is not re-litigated):
# apt-installing `libxcb1` into the image. Buildpacks cannot add apt layers
# cleanly, and the owner's ruling is to go headless rather than carry an X11
# closure into a server-side document pipeline. If the sidecar later moves to a
# purpose-built Dockerfile (a decision gated on id-404 / W4's LibreOffice
# `soffice` question, NOT on this task), that does not reopen this: headless
# remains correct there too.
